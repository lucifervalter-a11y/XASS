# Полная копия XASS и перенос сервера

В Mini App откройте **Инструменты → Данные → Весь сервер и перенос**.

- **Подготовить файл**: задайте пароль (от 12 символов), дождитесь готовности и нажмите **Скачать полный архив**. Получится один файл `.xass-server`.
- **Создать код переноса**: пароль генерируется автоматически и входит в код `XASS1.…`. Дождитесь готовности копии, скопируйте код на новый сервер. Он действует один час с момента создания и допускает одно скачивание. Кнопка **Отозвать код** запрещает последующее скачивание.
- Вход владельца обязателен. В браузере операции подтверждаются Passkey; внутри Telegram проверяется подписанный `initData`.
- Код содержит доступ ко всем данным, включая секреты. Не вставляйте его в чаты, командную строку, URL или GitHub. CLI запрашивает его скрыто через терминал. Код не сохраняется браузером и повторно не показывается после перезагрузки страницы.
- Если передача прервалась после начала скачивания, создайте новый код. Загруженные данные проверяются до восстановления. Владелец может повторно скачать обычную копию с новым билетом.

## Состав файла

Архив включает текущие файлы сайта и приложения, согласованный снимок основной БД, `data/`, медиа, аватары, проекты, ключи, `.env`, `.agent.env` (если есть) и фактически действующие настройки процесса. Внешние каталоги, указанные в настройках XASS, копируются отдельно и получают новые пути при восстановлении. Абсолютные пути сохранённых медиа в БД также переносятся.

Не включаются `.git`, виртуальные окружения, `node_modules`, Python-кэши и каталог текущих резервных копий. Зависимости переустанавливаются из сохранённых требований. Неизвестные символические ссылки не разыменовываются; их список есть в `manifest.json`. Это полный снимок приложения XASS, **не образ всех дисков Linux**: сторонние приложения, Docker-тома, системные пользователи, произвольные домашние каталоги и данные Windows-компьютеров не входят в него.

SQLite снимается через Backup API, включая подтверждённые WAL-транзакции; исходный файл БД не копируется «наживую». Для PostgreSQL используется `pg_dump --format=custom`, поэтому на источнике нужен `postgresql-client` совместимой версии. Лимит архива и распакованных данных — 32 ГБ. Для сборки, шифрования и восстановления требуется свободное место под несколько копий данных.

В CLI опция `--system-config` дополнительно включает доступные `/etc/nginx`, `/etc/letsencrypt` и systemd-конфигурацию XASS. Для TLS-ключей нужны права root. Недоступные системные файлы перечисляются в `unreadable_system_paths` манифеста; ошибка доступа к данным самого XASS прерывает выгрузку. Эти файлы восстанавливаются в `migration-system/` для проверки, автоматически чужую конфигурацию `/etc` они не заменяют.

Это снимок на момент создания. Новые сообщения, загруженные файлы и изменения после снимка в него не попадут. Для финального переключения приостановите изменения сайта, остановите старые backend и heartbeat-агент, затем сделайте **финальную копию через CLI**. Копирование из работающей Mini App удобно для предварительного переноса и проверки.

## Перенос по коду на новый сервер

На новом Ubuntu/Debian установите зависимости и запустите помощник:

```bash
sudo apt-get update
sudo apt-get install -y git python3 python3-venv
git clone https://github.com/lucifervalter-a11y/XASS.git /tmp/xass-migration-tools
sudo bash /tmp/xass-migration-tools/deploy/migrate.sh https://github.com/lucifervalter-a11y/XASS.git /opt/xass-new
```

Вставьте код по запросу. `/opt/xass-new` должен отсутствовать: помощник не перезаписывает существующую установку. Он проверит шифрование, восстановит файлы и БД, привяжет сохранённую ревизию к GitHub и установит Python-зависимости. Если исходный сервер использует PostgreSQL, сначала создайте **новую пустую БД**, установите `postgresql-client` и используйте CLI:

```bash
python3 -m venv /tmp/xass-migration-tools/.venv
/tmp/xass-migration-tools/.venv/bin/pip install -r /tmp/xass-migration-tools/requirements.txt
/tmp/xass-migration-tools/.venv/bin/python /tmp/xass-migration-tools/deploy/migrate.py receive --destination /opt/xass-new --postgres
```

CLI запросит URL новой БД скрыто. Непустая БД отклоняется. PostgreSQL восстанавливается одной транзакцией `pg_restore`; пользователи и права старого PostgreSQL не переносятся. В варианте с прямым CLI создайте Git-привязку по инструкции ниже.

Новая копия содержит `.migration-pending`: backend откажется стартовать до явной активации. Это предотвращает случайный запуск второго Telegram-поллера.

## Восстановление из файла и финальная копия

На старом сервере, в каталоге XASS:

```bash
sudo systemctl stop serverredus-backend
sudo systemctl stop serverredus-agent  # если этот сервис установлен
sudo .venv/bin/python deploy/migrate.py export --root "$PWD" --output /root/xass-final.xass-server --system-config
```

Команда дважды запросит пароль. Перенесите файл по SSH/SCP и восстановите в **новый каталог**:

```bash
/tmp/xass-migration-tools/.venv/bin/python /tmp/xass-migration-tools/deploy/migrate.py restore --archive /path/xass-final.xass-server --destination /opt/xass-final
```

Для PostgreSQL добавьте `--postgres`. Оригинальная `.env` сохраняется как `.env.source`; новая `.env` содержит действующие настройки и перенесённые пути. Посмотрите `migration-manifest.json` и список пропущенных ссылок. Если нужен обычный `tar.gz` для просмотра, команда `deploy/migrate.py decrypt --archive … --output …` расшифрует его с проверкой целостности. Такой файл содержит секреты без шифрования.

Помощник `migrate.sh` настраивает Git сам. После прямого CLI-восстановления привяжите новый каталог к сохранённому коммиту:

```bash
cd /opt/xass-final
git init -b main
git remote add origin https://github.com/lucifervalter-a11y/XASS.git
git fetch origin main
# Подставьте revision из migration-manifest.json:
git fetch origin SAVED_REVISION
git reset --mixed SAVED_REVISION
git branch --set-upstream-to=origin/main main
```

`reset --mixed` здесь используется только в новом восстановленном каталоге и не заменяет файлы снимка.

## Запуск и переключение домена

Проверьте сайт, профиль, количество сообщений, наличие медиа и ключей в подготовленной копии. Оставьте старые backend и агент остановленными. На **новом** Ubuntu/Debian:

```bash
sudo bash /opt/xass-final/deploy/activate-server.sh redvps.site --source-stopped
```

Скрипт устанавливает nginx/PHP, создаёт отдельного пользователя `xass`, Python-окружение, сервис `serverredus-backend` и конфигурацию сайта. Существующие одноимённые настройки он не перезаписывает. Доступ через HTTP предназначен для проверки сервера; для Mini App и Passkey нужен HTTPS.

Переключите A/AAAA-записи домена на новый IP и настройте TLS, например через Certbot, или адаптируйте сохранённую конфигурацию из `migration-system/`. Сохранение прежнего домена сохраняет привязку Passkey и адреса Windows-агентов. При смене домена потребуются новый вход, регистрация Passkey, адреса агентов и Telegram webhook. DNS и выпуск сертификата зависят от вашего домена, архив их не переключает.

Если на новом сервере уже есть nginx/systemd, настройте их вручную и снимите блокировку:

```bash
cd /opt/xass-final
.venv/bin/python deploy/migrate.py activate --source-stopped
```

Перед обслуживанием запросов убедитесь, что `PROFILE_PUBLIC_URL` и `service_base_url` соответствуют публичному адресу. Для Telegram webhook сохраните прежний HTTPS-адрес или повторите штатную настройку webhook. Сохранённые `.agent.env` и `migration-system` помогут переустановить локальный heartbeat-агент через `install.sh`; старый `run-agent.sh` может содержать пути старого сервера. Windows-клиенты перенос не переустанавливает.

Обновите GitHub Actions secrets `SSH_HOST`, `SSH_USER`, `SSH_PRIVATE_KEY`, `SSH_PORT` и путь `/home/red/serverredus` в deployment/backup workflows на новый каталог. Затем проверьте `/health`, вход в Mini App, профиль/аватары, получение нового business-сообщения, изменение и удаление сообщения, связь Windows-агентов. До завершения проверки сохраните исходный сервер выключенным, не удаляя его данные. Для возврата остановите новый backend, верните DNS и запустите исходный.

## Хранение и одноразовая доставка владельцу

`SERVER_BACKUP_DIR` по умолчанию `../.xass-backups` и обязан находиться вне корня сайта. Процесс backend должен иметь право создавать этот каталог. Файлы доступны API сутки; просроченные файлы и билеты удаляются при следующем запуске создания копии. Незавершённая более часа задача разрешает повторную попытку. Не меняйте каталог на общий публичный каталог файлов.

`Encrypted server backup` после успешного deploy проверяет `deploy/backup-request.json`. Запрос содержит только публичный RSA-ключ получателя, идентификатор и срок действия. На VPS создаётся зашифрованный архив с системной конфигурацией, затем ciphertext передаётся по SSH в GitHub artifact со сроком хранения 3 дня. Приватный ключ в репозиторий и Actions не передаётся. Повторный запуск сохраняет существующий снимок с тем же ID. После получения удалите файл запроса из Git; для следующей выгрузки нужен новый ID и свежий ключ получателя.

## Telegram после обновления

По умолчанию `TELEGRAM_MANAGEMENT_BUTTONS=false`: `/start`, старые команды управления и старые callback-кнопки направляют в Mini App, закреплённая reply-клавиатура удаляется при обращении. Меню XASS открывает Mini App. Сохранение переписок, уведомления об удалённых/изменённых сообщениях, away/quiet-режимы и точечные business-команды продолжают работать. Старые сообщения с меню физически остаются в истории до взаимодействия с ними. Для временной совместимости старый интерфейс можно включить переменной `TELEGRAM_MANAGEMENT_BUTTONS=true`.

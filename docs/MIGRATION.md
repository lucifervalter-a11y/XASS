# Перенос XASS на другой сервер

Перенос состоит из одного полного архива и восстановления на новом сервере. Архив содержит код именно этой установки, базу, настройки, ключи агентов, настройки входа iPhone, профиль, цитаты, проекты, аватары и серверные медиа. Повторно создавать бота и подключать каждый ПК не нужно, если сохранить тот же HTTPS-домен.

Доступ SSH к обоим серверам и управление DNS всё равно нужны. XASS не переносит чужой VPS, аккаунт хостинга или доменную регистрацию. Архивы Telegram, сохранённые **на дисках Windows-агентов**, остаются на этих ПК; в перенос входят их настройки и серверный индекс, а не сами диски.

## 1. Создать полный архив

На старом сервере, после обновления XASS:

```bash
cd /opt/serverredus
sudo systemctl stop serverredus-backend
sudo bash deploy/backup.sh /opt/serverredus /opt/serverredus-backups
```

Команда выведет имя `xass-server-ДАТА-ВРЕМЯ.tar.gz`, размер и SHA-256. Подставьте полученное имя в следующие команды. Полный архив содержит секреты: храните его вне папки сайта, передавайте через SSH/SCP и не публикуйте в Telegram-канале, GitHub или публичных загрузках.

Бэкап можно сделать и без остановки: SQLite копируется через online backup API, включая зафиксированные WAL-страницы; PostgreSQL — через `pg_dump`. Для финального переноса лучше остановить backend: так база, профиль и файлы относятся к одной точке времени, а изменения не теряются между экспортом и переключением. Если экспорт завершился ошибкой, исходные данные не меняются; чтобы вернуться к работе, выполните `sudo systemctl start serverredus-backend`.

Для произвольной папки и имени архива:

```bash
/opt/serverredus/.venv/bin/python /opt/serverredus/deploy/migrate.py export \
  --root /opt/serverredus --output /opt/serverredus-backups/xass.tar.gz
```

Стандартные и **реально настроенные** пути читаются из конфигурации сервера. Внешние файлы переносятся внутрь новой установки, пути в `.env` и ссылки на локальные медиа в базе приводятся к переносимому виду. Секреты `BOT_TOKEN`, `SETUP_API_KEY`, `AGENT_API_KEY`, VAPID и поколение PWA-сессий сохраняются. Старые невыполненные команды ПК отменяются при восстановлении, чтобы после переезда случайно не повторить перезагрузку или удаление файла.

Не копируются `.git`, виртуальные окружения, клиентский `pc_client/config.json`, кеш пакетов автообновлений и предыдущие архивы миграции. Код, локальные PHP-файлы конфигурации, установщик из настроенной папки releases и пользовательские ресурсы входят в архив. Символические ссылки и junction не обходятся: экспорт остановится с понятным сообщением, чтобы не получить неполную или непредсказуемую копию.

## 2. Передать архив

Из терминала компьютера можно сначала скачать файл, затем отправить на новый сервер:

```bash
scp user@OLD_IP:/opt/serverredus-backups/xass-server-ДАТА-ВРЕМЯ.tar.gz ./xass.tar.gz
scp ./xass.tar.gz user@NEW_IP:~/xass.tar.gz
```

`OLD_IP`, `NEW_IP` и `user` — адреса и SSH-пользователь ваших серверов. Вместо команд подойдёт SFTP-клиент. Старый сервер пока оставьте остановленным, но не удаляйте его данные.

## 3. Восстановить на новом сервере

Автоматическая подготовка рассчитана на свежие **Ubuntu 24.04+ / Debian 12+**, Python 3.11+, systemd и свободный порт 8000. Установите `git` и `python3`, если их нет, затем скачайте инструменты в отдельную папку:

```bash
git clone https://github.com/lucifervalter-a11y/XASS.git ~/xass-tools
cd ~/xass-tools
python3 deploy/migrate.py inspect ~/xass.tar.gz
sudo bash deploy/restore.sh ~/xass.tar.gz /opt/serverredus example.com
```

Вместо `example.com` укажите **прежний домен XASS**, без `https://` и без пути. `/opt/serverredus` должен отсутствовать или быть пустым. Скрипт не объединяет архив с существующей установкой и не перезаписывает существующую службу XASS.

Сначала проверяются формат, все размеры и SHA-256, пути и свободное место; затем данные распаковываются во временную закрытую папку и только после успешной проверки публикуются в целевой каталог. Симлинки, hardlink, обход `../`, абсолютные пути, дубликаты и повреждённые файлы отклоняются. По умолчанию распакованная копия ограничена 100 ГиБ; для больших архивов используйте ручной импорт с `--max-gib 500`.

После импорта скрипт устанавливает зависимости, создаёт `.venv`, службу `serverredus-backend` и nginx/PHP-FPM, сохраняет исходные секреты и ждёт `/health`. Для новой службы режим перезапуска явно переключается на systemd, даже если старый сервер использовал Docker/PM2. Установленный код привязывается к исходной Git-ревизии для дальнейших обновлений, когда она доступна на GitHub. Архивный код не запускается самим `migrate.py`; запуск приложения выполняет только явно выбранный `restore.sh`.

Если установка зависимостей или службы прервалась, восстановленные данные уже находятся в `/opt/serverredus`. Не запускайте повторно импорт в эту папку: завершите настройку по секции ниже. Ошибка не требует удаления исходного сервера.

## 4. Переключить домен и включить HTTPS

Измените A-запись домена на адрес нового сервера; проверьте также AAAA-запись, если использовался IPv6. Дождитесь обновления DNS и откройте входящие порты 80/443 в настройках хостинга. На новом сервере:

```bash
sudo certbot --nginx -d example.com
curl --fail https://example.com/health
sudo systemctl status serverredus-backend --no-pager
```

Сертификат выпускается для нового сервера, приватный ключ старого сертификата не копируется. До выпуска HTTPS вход iPhone/PWA и secure-cookie работать не должны. Если используется внешний reverse proxy/CDN с TLS, настройте его на новый origin и проверьте правильный HTTPS/Host forwarding.

Откройте Mini App, проверьте «Диагностику», профиль/цитаты/аватар, список ПК, блокировку экрана и загрузку агента. ПК с прежним доменом переподключатся при следующем запросе; браузер может потребовать повторный вход, но ключи доступа и настройки сохранятся. При polling не запускайте второй backend с тем же ботом одновременно. При webhook с тем же доменом адрес Telegram остаётся действительным.

Когда новый сервер проверен, старую установку можно оставить остановленной на время отката. Если перенос нужно отменить, остановите новый backend, верните DNS и включите старый. Изменения, появившиеся только на новом сервере, в старую копию автоматически не переносятся.

## Если меняется сам домен

Изменение IP и изменение домена — разные операции. Для незаметного переезда сохраняйте домен. Если домен меняется:

1. Настройте DNS и HTTPS нового адреса, укажите его в разделе подключения/веб-приложения Mini App и обновите адрес меню бота/webhook.
2. Если используете Telegram Login Widget, задайте новый домен командой `/setdomain` у BotFather.
3. На каждом ПК замените адрес сервера в агенте, сохранив имеющийся ключ, или импортируйте новый файл подключения из Mini App. Старый IP в конфигурации сам не узнает новый адрес.
4. На iPhone откройте новую защищённую ссылку из Mini App и добавьте приложение на домашний экран заново. Cookies и passkeys привязаны к домену; ключ Face ID для прежнего домена не переносится на другой домен, его нужно добавить заново.

## PostgreSQL

Экспорт автоматически выбирает `pg_dump` для `DATABASE_URL=postgresql+asyncpg://...`; установите пакет клиента PostgreSQL той же или совместимой версии до экспорта. Если `pg_dump` отсутствует или база недоступна, готовый архив не создаётся. Gzip встроен в Python, `zstd` не нужен.

На новом сервере создайте **пустую отдельную** базу и пользователя, установите `psql` и `pg_restore`. Укажите новый URL через переменную окружения, не через аргумент командной строки. Например, в интерактивном Bash:

```bash
read -rsp 'New PostgreSQL URL: ' XASS_RESTORE_DATABASE_URL; echo
export XASS_RESTORE_DATABASE_URL
sudo --preserve-env=XASS_RESTORE_DATABASE_URL bash deploy/restore.sh ~/xass.tar.gz /opt/serverredus example.com
unset XASS_RESTORE_DATABASE_URL
```

URL имеет вид `postgresql+asyncpg://USER:PASSWORD@HOST:5432/NEW_DATABASE`; специальные символы пароля кодируются для URL. Пароль передаётся клиенту через окружение, не печатается в отчёте. Скрипт откажется писать в непустую базу; загрузка дампа и подготовка состояния выполняются одной транзакцией. URL старого PostgreSQL никогда не используется для восстановления автоматически. Смена типа БД SQLite ↔ PostgreSQL не входит в этот перенос.

## Только импорт / другая система

Для уже подготовленной инфраструктуры или Windows доступен импорт без установки пакетов, запуска кода и изменения служб:

```bash
python3 deploy/migrate.py restore /private/xass.tar.gz --target /new/xass
```

Далее создайте виртуальное окружение, установите `requirements.txt` и запустите `uvicorn app.main:app` из восстановленного каталога. **Не используйте интерактивный `install.sh` поверх восстановленного `.env`:** он предлагает заново записать настройки и стандартные пути. Для Linux можно взять службу из `deploy/systemd/` и изменить `WorkingDirectory`/`ExecStart` на новый каталог. Для nginx оставьте API на localhost:8000, PHP-сайт и `/assets/`; запретите доступ к `.env`, исходникам, `/data/` и бэкапам, кроме публичной папки аватаров. При нестандартных путях передайте PHP-FPM `PROFILE_JSON_PATH`, `PROJECTS_JSON_PATH`, `QUOTES_JSON_PATH`, `SITE_CONFIG_JSON_PATH` из восстановленного `.env`.

Контрольные суммы обнаруживают повреждения, но не подтверждают авторство: восстанавливайте только собственный архив, переданный доверенным способом. Если уже вычисленное значение настройки содержит буквальное `${...}`, экспорт остановится: dotenv иначе повторно подставил бы переменную при восстановлении и мог изменить секрет. Устраните такую неоднозначную настройку явно до создания архива.

Чтение и импорт проверены на SQLite-файлах с WAL, внешними путями, состоянием агентов и повреждёнными архивами. PostgreSQL проверен тестами команд и транзакций; фактический `pg_dump`/`psql` нужно проверять с вашей БД. Запуск systemd/nginx/Certbot требует проверки на фактическом новом сервере; скрипт не подключается к нему сам. Дополнительные службы вне backend — например, отдельно установленный Linux-агент — не переносятся как системные unit-файлы: установите их отдельно, если использовали.

# XASS: завершение этапа надёжности

Эти изменения продолжают ветку `codex/xass-release-reliability` после iOS 0.21.3 (6).
Публикация кода или тестового установщика сама по себе не обновляет рабочий сервер,
Discord Developer Portal и стабильный канал приложения. Данные пользователя не
используются в автоматизированных аварийных проверках.

## Discord `/music`

1. В Discord Developer Portal, **General Information → Public Key**, скопировать
   публичный ключ приложения в `DISCORD_PUBLIC_KEY` (64 шестнадцатеричных символа).
   Bot Token и Client Secret для этого обработчика не нужны.
2. Указать `DISCORD_LISTEN_URL=https://redvps.site` или свой публичный HTTPS-сайт.
   Без значения используется `PROFILE_PUBLIC_URL`, затем `https://redvps.site`.
3. После выкладки backend настроить прямой маршрут nginx из
   `deploy/discord-interactions.nginx.conf` внутри существующего HTTPS server block.
   Перед reload обязательно `nginx -t`. PHP front controller также поддерживает
   этот маршрут, сохраняя исходные байты тела, подписи и реальные HTTP-статусы.
4. В **Interactions Endpoint URL** указать
   `https://redvps.site/api/discord/interactions`. Discord проверит подписанный PING.
   Уже зарегистрированная slash-команда `music` продолжает работать. Если команды
   ещё нет, зарегистрировать chat-input command с `name: music`, `type: 1`,
   `description: Что сейчас играет в XASS` через API приложения Discord.
5. В XASS включить публикацию музыки **на сайте**. Частная музыка и один лишь
   Discord Rich Presence не являются согласием на публичную карточку.

Обработчик проверяет Ed25519 по `timestamp + raw body`, свежесть timestamp и
ограничение тела 64 КиБ. PING возвращает PONG, `/music` — ответ type 4 с названием,
исполнителем, альбомом, позицией и ссылкой. Обложка выдаётся только для актуального
публичного трека, без ссылки на приватный поток и без билетов доступа.

Во время interaction нет SQL, файлового чтения и внешних HTTP-запросов. Фоновый
снимок обновляется каждые 0,5 с, истекает через 1,25 с, очищается при изменении
публикации/каталога. Ошибка обновления закрывает публикацию, а не продлевает устаревшие
данные. Локальная инвалидизация рассчитана на штатный однопроцессный backend;
между несколькими worker она ограничена TTL, а не мгновенным общим кэшем.
Медленное тело запроса прерывается через 0,75 с. Нагрузочные/сетевые задержки
реального сервера нельзя гарантировать одним модульным тестом.

Протокол: [официальная документация Discord](https://docs.discord.com/developers/interactions/receiving-and-responding).

## Серверный аудит и пакетный Undo

Все маршруты требуют существующую авторизацию владельца:

- `GET /api/mini/music/curation/tracks?after_id=0&limit=100` — курсорный список с
  `revision_token` для последующего подтверждения.
- `POST /api/mini/music/curation/audit` с `track_ids` (до 20) и `acoustic: true|false`
  — аудит выбранной группы, категории `no_artwork`, `no_lyrics`, `messy_tags`,
  версии записей и кандидаты в дубликаты. Это не отчёт о всех парах всей библиотеки:
  сравниваются выбранные треки. Неисследованные файлы не выдаются за заведомо пустые.
- `POST /api/mini/music/curation/batches` с `request_key`, `confirmed: true` и
  `changes: [{track_id, revision_token, tags: {title, artist, album}}]` (до 50).
- `GET /api/mini/music/curation/batches` — история владельца.
- `POST /api/mini/music/curation/batches/{id}/undo` с `confirmed: true` — атомарный
  откат всей пачки. Если хотя бы один трек уже изменён, ответ 409 и никакой частичной
  перезаписи. Повтор того же `request_key` не применяет пачку дважды.

Сервер правит каталог, не байты оригинального аудио. Журнал и теги сохраняются одной
транзакцией в новой таблице `music_curation_batches`, создаваемой штатным `init_db`.
Локальное изменение файлов на Windows остаётся в существующем инструменте
«Разобрать медиатеку» с полными резервными копиями и отдельным подтверждением.

Chromaprint и названия — только признаки кандидатов, не доказательство одинаковой
записи. `[Live]`, `[Acoustic]`, `[Remaster]`, `[Radio Edit]` разделяются. Граничная
тишина измеряется при пороге −60 dBFS в окнах до 6 секунд; неизвестная граница не
подменяется нулём. Отпечаток охватывает до 120 секунд и допускает временной сдвиг;
полное прослушивание разных редакций всё равно требуется. API удаления отсутствует.

Для серверного анализа контейнеров и реальных отпечатков нужны локальные `ffmpeg`,
`ffprobe`, `fpcalc` (Debian/Ubuntu: `ffmpeg libchromaprint-tools`). Без них API честно
показывает недоступный анализ; аудио не отправляется в AcoustID или облачную AI-службу.

## Windows и Handoff

Сборщик проверяет frozen Python 3.12, WinUI 3/Windows App SDK, bridge, манифест,
иконки и обязательные файлы пакета. Обновлятор повторно проверяет SHA-256/размер
непосредственно перед остановкой приложения. Тест аварии использует настоящий
Inno Setup в отдельном каталоге: прерывание копирования, завершение дерева процессов,
возврат предыдущих бинарников, побайтная сохранность config/E2E/SQLite/медиа.
Отклонённый SHA не запускает циклическую автоустановку; ручной повтор остаётся явным.

Передача звука остаётся PREPARE → STOP_PREV с точной позицией → START_NEW.
Подтверждения связаны с конкретной попыткой, треком и свежим heartbeat. Потерянная
после сбоя ссылка на уже созданную команду восстанавливается по idempotency key.
Неопределённый START не считается тишиной и не даёт исходному устройству автоматически
возобновить звук. Выбор «Возобновить здесь» / повтор передачи остаётся явным.

При несовместимом декодере используется FLAC или MP3 320 кбит/с. Перекодирование
не восстанавливает качество исходного сжатого файла и не изменяет оригинал.
Ключ кэша учитывает профиль кодирования, поэтому старый MP3 256 кбит/с не переиспользуется.
Совместимая копия готовится с ограничением времени и места до подтверждения READY,
а затем отдаётся из кэша с поддержкой диапазонов; это не неограниченный ffmpeg-поток
на каждое подключение. Уже доставленную отключённому ПК команду сервер физически
отозвать не может: при неопределённом результате новый звук автоматически не запускается.

## Верификация

Новые тесты находятся в `tests/test_discord_interactions.py`,
`tests/test_php_music_proxy.py`, `tests/test_music_curation*.py`,
`tests/test_music_handoff_reliable.py`, `tests/test_music_compatibility.py` и
`windows/tests/test_native_*.py`, `windows/tests/test_real_installer_rollback.py`.
Полные backend/browser, native Windows installer и iOS проверки должны проходить
на одной итоговой ревизии перед публикацией комплекта. CI не доказывает реальный
звук на физической паре iPhone–ПК, настройку Developer Portal или поведение VPN.
Прерывание посреди копирования проверяется настоящим Inno на изолированном тестовом
payload; откат полного установщика проверяется с внедрённым сбоем health-check.
Установочный smoke проверяет ту же версию; межверсионная миграция этим не доказана.
